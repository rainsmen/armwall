## 0. 摘要

**症状**：路由器 passwall 以 SOCKS5 把全网流量交给 ArmWall；Android Google Play 能列出可更新应用，点击更新后一直转圈；手机端 App 直接使用同一节点则可以更新。

**结论**：同一症状在两台机器上由不同机制造成，手机端 App（VPN 模式）同时接管 IPv6 与 UDP，所以能绕过所有这些机制。

| 场景 | 主因 | 位置 |
| --- | --- | --- |
| `.233`，`bypass_cn` 模式 | `geosite-cn` 把 Play 使用的 `www.gstatic.com`、`redirector.gvt1.com`、`dl.google.com` 等判为国内直连；ArmWall 在 DNS 模块关闭时不给 sing-box 任何解析器，直连域名退化到主机 `systemd-resolved` 并超时；选中的 naive 节点拒绝 UDP | ArmWall 配置生成逻辑 |
| `.217`，`global` 模式 | passwall 的 IPv6 TProxy 把非国内 IPv6 TCP 重定向到 `[::]:1041`，而 ipt2socks 只绑定了 IPv4，连接被原地丢弃；UDP 一律不代理，QUIC 黑洞；`tcp_redir_ports` 不含 GMS 的 5228–5230 | 路由器 passwall |

**已执行（路由器，全部验收通过）**

| 编号 | 改动 | 效果 |
| --- | --- | --- |
| B0 | `/usr/share/passwall/app.sh` 三处 ipt2socks 启动命令补 `-B ::` | IPv6 TCP 经 TProxy → ArmWall → 节点，端到端 204，2 MB 下载 1.8 MB/s |
| C | `udp_proxy_drop_ports=443` | 境外 QUIC 立即丢弃，应用秒级回落 TCP；国内 QUIC 不受影响 |
| D | `tcp_redir_ports=1:65535` | 5228/5229/8443 等端口经代理，GMS 推送可达 |

**待办**：用户手机复测 Play 更新；ArmWall 代码层改进（§4）独立排期。

### 1.1 组件

| 组件 | 事实 |
| --- | --- |
| 路由器 `192.168.10.1` | ImmortalWrt 21.02，passwall 4.68（iptables 模式 `use_nft=0`），ipt2socks 1.1.3，chinadns-ng 2023.10.28，dns2tcp 1.1.0，xray 1.8.3。`tcp_node` = Socks 节点 `192.168.10.217:11080`；`tcp_proxy_mode=chnroute`；`udp_node=nil`；`ipv6_tproxy=1`；`filter_proxy_ipv6=1`。LAN 下发原生 IPv6 前缀 `2409:8a04:5381:c8f1::/64` 与 ULA `fdca:6736:ba8d::/64` |
| `.217`（当前在用） | `mode=global`，DNS 模块开（`dns-in 192.168.10.217:53`，客户端未使用），`udp_outbound=same`，选中节点 naive/https，服务器解析为 **IPv4 154.26.184.211**（并非纯 IPv6 节点），naive 到节点全为 IPv4 会话。另有一个非 ArmWall 管理的 `naiveproxy.service` 监听 `0.0.0.0:1080` 且无鉴权 |
| `.233`（已停用） | `mode=bypass_cn`，DNS 模块关，选中 naive 节点；自 2026-11-01 23:17 后再无局域网流量 |
| 节点 | naive（https 与 quic 两种传输）为主，另有 anytls/hysteria2/vmess 订阅节点；节点出口可达 IPv4 与 IPv6 |
| DNS | 手机使用路由器 dnsmasq → chinadns-ng（gfwlist 域名过滤 AAAA）→ dns2tcp → 8.8.8.8:53；路由器自身到 8.8.8.8:53 的 TCP 被 TProxy 经 ArmWall 出去。`*.googleapis.com` 等被自定义域名表直送 dns2tcp，**绕过 chinadns-ng，AAAA 不被过滤** |

### 1.2 链路

```
手机 ──IPv4 TCP──▶ 路由器 PREROUTING/PSW ──TPROXY:1041──▶ ipt2socks ──SOCKS5(IP 目标)──▶ ArmWall mixed-in:11080
                                                                                       └─▶ sing-box 路由 ──▶ naive 本地桥接 ──▶ 节点 ──▶ 目标
手机 ──IPv6 TCP──▶ 路由器 PSW(v6) ──TPROXY [::]:1041──▶ （修复前无监听者，丢包；修复后同上）
手机 ──UDP/QUIC──▶ 路由器 PSW ──RETURN──▶ 直连运营商（境外被黑洞；现对 443 显式 DROP）
```

两个贯穿全文的事实：

1. **ArmWall 收到的全是 IP 目标。** `.217` 最近 5 万条入站记录中 IP 目标 18 415 条、域名 12 条。sing-box 第一条规则 `action: sniff` 从 TLS ClientHello 取回 SNI，之后的域名规则用 SNI 匹配。
2. **ArmWall 当前所有 naive 节点都不能中继 UDP。** 对 12000（quic）、12002/12006（https）做 SOCKS5 UDP ASSOCIATE 全部返回 `rep=7`（naive 154.0.8037.49）；passwall `app.sh:667` 也会打印「Naiveproxy不支持UDP转发！」。

## 2. 根因分析

### 2.1 场景一：`.233`，`bypass_cn` 模式（ArmWall 侧）

生效规则：`sniff → ip_is_private→direct → geosite-ads→block → [geosite-cn, geoip-cn]→direct → final=naive`，配置自 10-31 17:01 起未变。

**A. `geosite-cn` 包含 Google Play 所用域名。** 对生产机 `geosite-cn.srs` 反编译后按 sing-box 语义精确匹配：

| 域名 | 匹配 | 后果 |
| --- | --- | --- |
| `redirector.gvt1.com`（APK 下载跳转） | `domain` | direct |
| `dl.google.com` | `domain` | direct |
| `www.gstatic.com` | `domain` | direct |
| `redirector.c.play.google.com` | `domain` | direct |
| `play.googleapis.com` | 不命中 | 代理（所以更新列表能显示） |

passwall 的 DNS 对 `redirector.gvt1.com`、`dl.google.com` 返回中国移动 GGC 地址（`223.106.89.225`、`120.253.253.225`），直连可达；但 `www.gstatic.com`（`142.251.x`）与 `android.clients.google.com` 直连被黑洞。日志中 11-01 21:00–23:17 的 59 万条连接里：

```
ERROR open connection to 142.251.214.99:443 using outbound/direct[direct]: dial tcp ...: i/o timeout
ERROR open connection to 142.251.45.3:443   using outbound/direct[direct]: dial tcp ...: connection reset by peer
```

目标以 IP 形式到达却被判 direct，而这些 IP 均不在 `geoip-cn`，唯一一致的解释是 sniff 得到的 SNI 命中了 `geosite-cn`。sing-box 5 秒放弃后客户端反复重试，UI 持续转圈。

**B. DNS 模块关闭时 ArmWall 不输出任何解析器。** `config.go` 只在 `DNS.Enabled` 时写 `dns` 块与 `route.default_domain_resolver`。被判 direct 且带域名的连接由主机 `systemd-resolved`（首选路由器 IPv6 ULA DNS）解析，受控探测：

```
ERROR [10.24s] open connection to www.gstatic.com:443 using outbound/direct[direct]:
      lookup www.gstatic.com: (exchange6: context deadline exceeded)
```

`resolvectl query www.gstatic.com` 在 `.233` 上挂死超过 120 秒；同一域名经节点远程解析 0.5–0.7 秒返回。（早先用 `c.android.clients.google.com` 探测得到的 `empty result` 不作数：该主机名不存在 A 记录。）

**C. UDP 黑洞。** 通过 `mixed-in` 做 UDP ASSOCIATE 全部无应答，日志 `socks5: request rejected, code=7`。`udp_outbound` 为空时 UDP 跟随 TCP 节点，ArmWall 没有任何提示。

### 2.2 场景二：`.217`，`global` 模式（路由器侧）

ArmWall 本身无问题：全局模式没有国内直连规则，受控探测后所有 Google 主机均 `outbound/socks[node-…]` 出站，4 MB Range 下载 3.4–3.8 MB/s，最近 5 万行日志仅有探测自造的 2 条错误。真正到不了 ArmWall 的是两类流量：

**R1. IPv6 TCP 被路由器黑洞。** passwall 启动的是
`ipt2socks_TCP -l 1041 -b 0.0.0.0 -s 192.168.10.217 -p 11080 -T`，只监听 `0.0.0.0:1041`（IPv6 侧仅默认的 `::1:1041`）。ip6tables 规则
`-p tcp … ! --match-set passwall_chnroute6 dst -j PSW_RULE` 与 `-m mark 0x1 -j TPROXY --on-port 1041 --on-ip ::` 把所有非国内 IPv6 TCP 重定向到 `[::]:1041`，无监听者，SYN 被丢弃。
对照实验：从 `.217` 发 `curl -6` 到 Google 期间，两条规则计数分别 +23/+22，ArmWall 侧 IPv6 目标仍为 0，请求 6–8 秒超时；IPv6 到百度（在 chnroute6 内，不重定向）正常。
手机拿到 AAAA（`*.googleapis.com` 绕过 chinadns-ng 过滤）后优先走 IPv6，于是每条连接等到超时。

**R2. UDP 完全不代理。** `udp_node=nil`，v4/v6 链均 `-p udp -j RETURN`；ArmWall 日志中 UDP 会话数为 0。QUIC 直连境外被黑洞，Google 应用需等握手超时后回落 TCP。

**R3. `tcp_redir_ports` 不含 5228–5230、8443。** GMS/FCM 长连接直连被封，Play 的下载调度依赖这些连接。

### 2.3 其它发现

- `.233` 的 sing-box 自 11-01 23:17 起无局域网流量，说明用户早已切到 `.217`，`.233` 场景的结论用于解释此前现象与修正 ArmWall 代码，不影响当前网络。
- 本机（`.238`）的 IPv6 报 `Network is unreachable`，是本机路由问题，未用作证据。
- `.217` 的 `naiveproxy.service` 在 `0.0.0.0:1080` 提供无鉴权 SOCKS，整个局域网可用；如非有意，应改为 `127.0.0.1`。

## 3. 已执行的处置与验收

### 3.1 B0：让 ipt2socks 监听 IPv6（13:26–13:30）

ipt2socks 1.1.3 自带 `-B/--listen-addr6`（默认 `::1`），passwall 4.68 的 `app.sh` 第 324、650、906 行只传了 `-b 0.0.0.0`。不升级任何软件包，补一个参数即可。

```sh
cp /usr/share/passwall/app.sh /usr/share/passwall/app.sh.bak-20261103-1326
sed -i 's/-b 0\.0\.0\.0 -s/-b 0.0.0.0 -B :: -s/' /usr/share/passwall/app.sh   # 命中 3 行，sh -n 通过
/etc/init.d/passwall restart
```

重启后 `ipt2socks_TCP -l 1041 -b 0.0.0.0 -B :: -s 192.168.10.217 -p 11080 -T -v`，`netstat` 同时出现 `0.0.0.0:1041` 与 `:::1041`。执行前已用临时进程验证该内核可绑定 `[::]`。

| 验收项（以 `.217` 为带原生 IPv6 的局域网客户端） | 结果 |
| --- | --- |
| `curl -6 https://play.googleapis.com/generate_204` | 204，0.94 s，远端 `2001:4860:4843:400::` |
| 强制 AAAA 的 `www.google.com`、`redirector.gvt1.com`、`www.gstatic.com` | 均 204，0.6–1.0 s |
| IPv6 2 MB Range 下载 `dl.google.com` | 206，1.8 MB/s |
| ArmWall 日志 | 首次出现成对的 `inbound … to [2001:4860:…]:443` / `outbound/socks[node-…] … to [2001:4860:…]:443`，无新 ERROR |
| 路由器 v6 TPROXY 计数 | 随测试递增且连接成功 |
| IPv4 回归（`.217` 与本机）、IPv6 到百度 | 全部正常 |

预期且无害的现象：不加 `--resolve` 时 `curl -6 www.google.com` 报连不上，因为路由器对 gfwlist 域名不返回 AAAA（chinadns-ng `-N=gt` 生效），客户端自然改走 IPv4 并被代理；有 AAAA 的域名现在也被正确代理。`www.gstatic.com` 在 `.217` 本机解析偶发超时是其 `systemd-resolved` 首选 IPv6 ULA DNS 的老问题，不影响局域网客户端。

### 3.2 C + D：UDP 443 丢弃与 TCP 全端口（13:42–13:47）

```sh
cp /etc/config/passwall /etc/config/passwall.bak-20261103-1342
uci set passwall.@global_forwarding[0].udp_proxy_drop_ports='443'
uci set passwall.@global_forwarding[0].tcp_redir_ports='1:65535'
uci commit passwall && /etc/init.d/passwall restart
```

生成规则：TCP TPROXY 规则不再带端口列表；新增 `-p udp -m multiport --dports 443 … -j DROP` 仅匹配 FakeIP、分流列表、黑名单、非 chnroute 目的地（`iptables.sh:511-519`）。`:::1041` 在重启后仍在，B0 持久。

| 验收项 | 结果 |
| --- | --- |
| `.217` 连接 `mtalk.google.com:5228/5229`、`www.google.com:8443` | 全部连通，ArmWall 日志出现对应流量并由节点出站 |
| 向 `8.8.8.8:443`、`[2001:4860:4860::8888]:443` 各发 7 个 UDP 包 | v4/v6 DROP 计数各 +7 |
| 向国内 `223.5.5.5:443` 发 7 个 UDP 包 | DROP 计数不变 |
| 回归：`play.googleapis.com` IPv4/IPv6、百度、本机经 passwall | 全部正常，约 0.65 s |

**与「OpenWrt 自行启用 naive 节点」的关系**：C、D 都只是 iptables 匹配，与节点类型无关。naive 任何传输都不能中继 UDP，境外 QUIC 本就出不去，C 只是把黑洞变成快速失败；D 对本地 naive 同样经 ipt2socks，B0 补丁同样生效。只有将来换成支持 UDP 的节点并开启 UDP 代理时，才需要取消 C 以放行 QUIC。另注意「dmit udp」是 quic 传输，节点链路走 UDP 易受运营商 QoS 影响（见 `INCIDENT-REPORT-2026-10-29.md`），主节点建议用 https 传输。

## 4. ArmWall 代码层改进方案（PR1 已实现并部署，2026-11-03）

以下改动针对 §2.1 的 A/B/C，使 ArmWall 在 `bypass_cn` 模式下也不再踩同类陷阱。**§4.1–4.4（PR1）与 §4.5（诊断），以及 B5、B6 均已实现**，二进制 `0.6.0-dev` 已部署到 `.233`（测试）与 `.217`（生产），验收见 §7。§4.5 见 §8。

实现与本文原方案的两处偏差，均为实测后修正：

1. **未加入 `resolve` 动作。** 原方案建议在 `geosite-cn` 与 `geoip-cn` 之间插入 `{"action":"resolve"}`，实测发现它会把上游网关（passwall）已经选好的目标 IP 重新解析：例如 `redirector.gvt1.com` 按国内 GGC 解析到 `223.106.89.225` 时会被换成境外地址。改为只依赖 sniff 出的 SNI 命中域名规则，`geoip-cn` 仅用于本身就是 IP 的目标，行为与之前一致但不再有重新解析的副作用。
2. **UDP 兜底规则必须排在两条国内规则之后。** 拆分 CN 规则后若按原位置插入，`geosite-cn`（域名型）匹配不到上游送来的 IP 目标，国内 UDP 会被一并阻断；实测发现后调整次序，并加入断言测试 `TestNaiveTCPOutboundBlocksUDP` 检查该次序。

实现要点：`dns` 块始终生成（`remote-dns` 经 TCP 出站做 DoH + `direct-dns`，国内域名走 `direct-dns`），`route.default_domain_resolver` 指向 `remote-dns`，每个出站带 `domain_resolver`（`direct` → 国内、代理 → 远程），移除已废弃的 `dns.independent_cache`；`bypass_cn` 拆成 `geosite-cn` → direct、`geoip-cn` → direct 两条；新增内置 + 可编辑的强制代理域名后缀规则置于国内规则之前；有效 UDP 出站为 naive 时输出 `{"network":"udp","outbound":"block"}` 并打印告警。Store 新增 `force_proxy_domains`（含 SQLite 读写、导入校验、`POST /api/routing` 字段与「分流与 DNS」页输入框）。新增测试：`TestConfigAlwaysEmitsDNSResolver`、`TestForceProxyRulePrecedesCNBypass`、`TestNaiveTCPOutboundBlocksUDP`，并更新 `TestConfigACLAndDNS` 对解析器方向的断言。

### 4.1 永远生成 `dns` 块与 `route.default_domain_resolver`

即使 `DNS.Enabled=false`（不监听 `dns-in`），也输出：

```json
"dns": {
  "servers": [
    {"type":"https","tag":"remote-dns","server":"1.1.1.1","path":"/dns-query",
     "tls":{"enabled":true,"server_name":"cloudflare-dns.com"},
     "detour":"<tcpOutbound>","domain_resolver":"direct-dns"},
    {"type":"udp","tag":"direct-dns","server":"223.5.5.5","server_port":53}
  ],
  "rules":[{"rule_set":["geosite-cn"],"action":"route","server":"direct-dns"}],
  "final":"remote-dns","strategy":"prefer_ipv4"
},
"route": {"default_domain_resolver":"remote-dns", ...}
```

每个出站设置 `domain_resolver`：`direct` → `direct-dns`，代理节点 → `remote-dns`。现有代码在 DNS 启用时写的是 `default_domain_resolver: "direct-dns"`，会让境外域名用国内 DNS 解析后再交给代理，方向反了，一并修正。注意 `domain_resolver` 不能写在 `route.rules` 条目上（1.14.4 报 unknown field），只能写在出站与 DNS 服务器上。

### 4.2 强制代理规则置于国内直连规则之前，并拆分 CN 规则

```json
{"domain":["redirector.gvt1.com","dl.google.com","www.gstatic.com","redirector.c.play.google.com"],
 "domain_suffix":["googleapis.com","clients.google.com","gvt1.com","gvt2.com"],
 "outbound":"<tcpOutbound>"},
{"rule_set":["geosite-cn"],"outbound":"direct"},
{"action":"resolve","strategy":"prefer_ipv4","server":"direct-dns"},
{"rule_set":["geoip-cn"],"outbound":"direct"}
```

建议做成 Store 中可编辑的 `ForceProxyDomains`（内置上述默认值）。拆分 `[geosite-cn, geoip-cn]` 使域名规则优先于 IP 规则，避免被污染的国内 IP 把境外域名拖去直连。

### 4.3 UDP 兜底

- 生成配置时识别 TCP 出站为 `naive` 且 `udp_outbound` 为空/same，自动追加 `{"network":"udp","outbound":"block"}`，或把 UDP 指向第一个支持 UDP 的已启用节点（anytls/hysteria2/vmess/vless/trojan/shadowsocks）。
- 节点列表与「分流与 DNS」页对 naive 节点显示「不支持 UDP」。

**SOCKS5 UDP ASSOCIATE 探测（Python，无依赖）**

```python
import socket, struct
def udp_assoc(proxy, port, dst="8.8.8.8", dport=53):
    t = socket.create_connection((proxy, port), timeout=6); t.settimeout(6)
    t.sendall(b"\x05\x01\x00"); assert t.recv(2) == b"\x05\x00"
    t.sendall(b"\x05\x03\x00\x01" + b"\x00"*4 + struct.pack(">H", 0)); r = t.recv(64)
    if r[1] != 0: return "REJECTED rep=%d" % r[1]
    relay = (socket.inet_ntoa(r[4:8]), struct.unpack(">H", r[8:10])[0])
    if relay[0] == "0.0.0.0": relay = (proxy, relay[1])
    q = b"\xab\xcd\x01\x00\x00\x01\x00\x00\x00\x00\x00\x00" + b"\x03www\x07gstatic\x03com\x00\x00\x01\x00\x01"
    u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u.settimeout(5)
    u.sendto(b"\x00\x00\x00\x01" + socket.inet_aton(dst) + struct.pack(">H", dport) + q, relay)
    try: return "UDP WORKS %d bytes" % len(u.recvfrom(4096)[0])
    except socket.timeout: return "NO REPLY"
```

## 9. 域名解析根因与 v0.6.1（2026-11-03 22:00–22:40）

### 9.1 修正：不是 systemd-resolved 的 IPv6 ULA 上游

§8 里「主机解析器失败源于 resolved 优先使用路由器 ULA DNS」的判断**错误**。实测：

| 测试 | 结果 |
| --- | --- |
| 两台机器 `resolvectl status` | `Current DNS Server` 都是 192.168.10.1（IPv4） |
| 从 .233 分别问 192.168.10.1 与 fdca:6736:ba8d::1 | `www.gstatic.com` 两者都超时；`github.com`、`play.googleapis.com` 两者都秒回 |
| 从 .233 直接问 223.5.5.5（3 次） | `www.gstatic.com`/`ssl.gstatic.com` 全部超时；百度、腾讯、play.googleapis 全部 0.00 s |
| 经 .217 的 SOCKS5 做 TCP DNS 到 8.8.8.8:53 与 1.1.1.1:53 | 只有 gstatic 无应答，百度/腾讯秒回 |
| 经 .233（DNS 模块关闭）做同样查询 | gstatic 正常返回 |

### 9.2 真正的因果链

1. 路由器 passwall 对 `*.gstatic.com` 使用专用上游 `server=/.gstatic.com/127.0.0.1#15353`（dns2tcp → 对 8.8.8.8:53 的 TCP 查询，经 passwall 的 TPROXY 走 ArmWall）。
2. ArmWall（.217，DNS 模块开且「DNS 劫持」开）的 `{"protocol":"dns","action":"hijack-dns"}` 规则**截获**了这条查询，用自身解析器回答而不转发。
3. ArmWall 把 `*.gstatic.com` 当作国内域名（`geosite-cn` 确实收录 `www.gstatic.com`）交给 `direct-dns`（223.5.5.5），而这条线路的国内解析器对该名字不返回任何结果。
4. 于是 ArmWall 无应答 → dnsmasq 等超时 → 局域网内所有客户端以及两台 ArmWall 自身的解析都被卡住。今早可用是因为 dnsmasq 当时持有该名字的缓存，TTL 到期后冷查询暴露了问题；**当天的三处 passwall 改动不是原因**（已用 .233 对照排除）。

### 9.3 v0.6.1 的两项修复与验证

| 改动 | 验证 |
