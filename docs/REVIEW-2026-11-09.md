## 1. 问题一：wikih6 中转节点 URL test 失败

### 1.1 证据

数据库中的节点：`type=naive`，`server=hknat.<域名>`，`port=4435`，`server_name=wikih6.<域名>`。导入时 `sni` 参数已正确保存（`subscription.go:202`），但生成的 `/etc/armwall/naive/0004.json` 里只有：

```json
"proxy": "https://<用户>:<密码>@hknat.<域名>:4435"
```

| 实验（在 `.217` 上） | 结果 |
| --- | --- |
| 用 `openssl s_client` 连接 `hknat:4435`，SNI 设为 `hknat.<域名>` | 返回的证书 SAN 只有 `wikih.<域名>`，主机名不匹配（返回码 62） |
| 同上，SNI 设为 `wikih6.<域名>` | 返回 `wikih6.<域名>` 的证书 |
| 经当前配置的 naive（`127.0.0.1:12009`）请求 `generate_204` | 返回 `000`；naive 报 `ERR_PROXY_CERTIFICATE_INVALID` |
| 对照：同一台香港主机上的 `hknat:4431` 节点（12007） | `204` |
| 临时 naive：URL 主机写 `wikih6.<域名>`，并加上 `host-resolver-rules=MAP wikih6.<域名> hknat.<域名>` | `204`，出口 US。写在 JSON 配置里或作为命令行参数都可用，MAP 的目标写主机名或 IP 都可以 |

面板的 ping 只是对 `hknat.<域名>` 发 ICMP，不经过 TLS，所以能 ping 通。URL test 的路径是 sing-box → 本地 naive SOCKS → TLS 握手，证书问题出在这一步。

### 1.2 根因

- ArmWall 生成节点配置有两条路径。sing-box 原生出站会读取 `ServerName`（`config.go:464`）。naive 节点则由外部 naive 进程连接，它的配置由 `naiveBindings` 只用 `Server:Port` 拼出（修复前的 `naive.go:45`），`ServerName` 和 `Insecure` 都没有用上。
- NaiveProxy 没有独立的 SNI 参数，SNI 就是 proxy URL 里的主机名。要实现"连接地址 A、用域名 B 握手"，只能把 URL 主机写成 B，再用 `host-resolver-rules` 把 B 映射到 A。安卓客户端也是这么做的。
- 这行代码从 `a9ef16e`（2026-07-26）起就没变过；测试只覆盖了"连接地址就是证书域名"的情况；其余 9 个 naive 节点的 SNI 都为空，所以问题一直没暴露。

### 1.3 修复（`2b26eef`，已推送，CI 通过，未发布 release）

- `naive.go`：SNI 不为空且和服务器地址不同时，URL 主机改用 SNI，并生成 `"host-resolver-rules": "MAP <SNI> <服务器地址>"`（IPv6 地址自动加方括号）；格式不合法的值不会写进规则。
- `validate.go`：naive 节点的服务器地址必须是主机名或 IP，SNI 必须是主机名。
- 「跳过证书验证」：naive 154 的命令行没有对应参数（实测 `--ignore-certificate-errors`、`--insecure` 都无效），sing-box 内置的 naive 出站会直接报错 `insecure is not supported on naive outbound`。因此做了以下处理：
  - 编辑页对 naive 禁用这个复选框，并说明原因；
  - 新增、编辑节点的接口遇到这个设置直接拒绝（返回 400）；
  - 链接导入、订阅更新、备份恢复时自动清除这个设置，链接导入的返回结果里会给出清除的数量（`ignored_insecure`）。
- 编辑页对 naive 节点显示 TLS SNI 输入框。
- 新增测试，覆盖中转节点的配置生成（主机名、IPv4、IPv6、SNI 与地址相同、空值、异常值）、链接导入、接口拒绝和备份恢复。

### 1.4 部署与验证

| 主机 | 验证 |
| --- | --- |
| `.233`（arm64） | 临时导入 wikih6 的分享链接，并故意加上 `insecure=1`：生成的配置正确，接口返回 `ignored_insecure:1`；TCP 测试 30ms，URL test 2243ms，出口 US；接口拒绝带 insecure 的 naive 节点（400）；用无头浏览器检查了编辑页；删除临时节点后，naive 配置和部署前一致 |
| `.217`（armv7） | 换上新版本并执行 `armwall --write-config`；`sing-box.json` 和部署前逐字节一致；wikih6 URL test 1309ms，出口 US |

### 1.5 运维注意

- 重启 armwall **不会**重新生成 `/etc/armwall/naive/*.json` 和 `sing-box.json`。升级后需要执行一次 `armwall --write-config`，或者改动一次配置。
- 手动执行 `--write-config` 时，要按 systemd 的顺序加载环境变量：先设置 unit 里的 `Environment=` 值（`ARMWALL_LISTEN=127.0.0.1:8080 ARMWALL_PROXY_PORT=11080 ARMWALL_TPROXY=1 ARMWALL_TPROXY_PORT=11081`），再 source `/etc/armwall/armwall.env`，后者会覆盖前者。
- 漏掉 `ARMWALL_TPROXY` 会导致生成的 `sing-box.json` 缺少 tproxy 入站。本次在 `.217` 上发生过一次，当时 sing-box 没有重启，运行未受影响；随后已按正确顺序重新生成，并和部署前的文件逐字节核对一致。
- 部署前，`.217` 的 `0004.json` 已经被手工改成了和修复后相同的内容（11-09 19:14），是谁改的尚未确认。

## 2. 问题二：面板 ping hknat 空报错

### 2.1 ping 卡在反向解析

| 命令（在 `.233` 上） | 耗时 | 结果 |
| --- | --- | --- |
| `timeout 3 ping -c1 -W2 hknat.<域名>`（模拟面板） | 3030ms | 被强制结束，没有任何输出 |
| `ping -c1 -W2 hknat.<域名>` | 5081ms，有时超过 9 秒 | 成功 |
| `ping -n -c1 -W2 hknat.<域名>`（不做反向解析） | 256ms | 成功 |
| 直接 ping IP | 18ms | 成功 |

- ping 收到回包后，会对回包的来源地址做反向解析（PTR 查询）。hknat 只有 IPv6 地址，这一步一直卡住。
- 面板调用的是 `runCommandTimeout(3s, "ping", "-c", "1", "-W", "2", host)`（`api_nodes.go:539`）。ping 往管道写输出时会先放进缓冲区，进程被强制结束时这部分内容就丢了（实测输出 0 字节），所以面板只显示 `ping failed:`。
- 已排除服务权限的原因：armwall 以 root 运行、没有限制任何能力；在命令行里加上同样的 3 秒时限，现象完全一样。

### 2.2 DNS 链路

```
局域网主机 ──UDP 53（dns_redirect：发往任何地址都会被劫持）──▶ 路由器 dnsmasq :53
  └─▶ chinadns-ng :15354（-f）
        ├─ 国内上游 -c 192.168.1.1（光猫的 DNS 代理）──▶ 中国移动 DNS
        └─ 可信上游 -t 127.0.0.1#15353 dns2tcp ──TCP──▶ 8.8.8.8（经 passwall → ArmWall）
```

在路由器上逐级查询境外 IPv6 的反向解析（每一级都用新地址）：

| 层级 | 结果 |
| --- | --- |
| dns2tcp :15353（可信上游） | 180–198ms，NXDOMAIN |
| 光猫 192.168.1.1（国内上游） | 超时（10 秒） |
| chinadns-ng :15354 | 超时（10 秒） |
| dnsmasq :53 | 超时（10 秒） |

可信上游其实已经给出了答案，但国内上游不回复时，chinadns-ng 不会采用这个答案，整条查询就挂起了。推测和公平模式 `-f` 有关：它必须等到国内上游的结果才能做判断。这一点没有通过阅读源码确认。

### 2.3 中国移动 DNS 解析不了 `ip6.arpa`

光猫上网连接的 DNS 是自动获取的：IPv4 为 `111.11.1.1`、`111.11.11.1`，IPv6 为 `2409:8008:2000::1`、`2409:8008:2000:100::1`。以下都在路由器上直接查询（路由器自己发出的查询不受 dns_redirect 影响）：

| 查询 | 光猫（192.168.1.1 / fe80::1） | 中国移动 DNS（4 个地址） | 公共 DNS 119.29.29.29 |
| --- | --- | --- | --- |
| 境外 IPv6 反向（hknat 所在的 APNIC 段、HE、Cloudflare） | 超时 | **全部超时**，UDP 和 TCP 都一样 | 62ms |
| `ip6.arpa` 本身的 SOA/NS（抽测 111.11.1.1 和 2409:8008:2000::1） | — | **超时** | 208ms / 690ms |
| APNIC、ARIN、HE 各级反向区的 SOA | — | 超时 | 93–342ms |
| 中国移动 IPv6 段的反向 | 13ms | 5–16ms | — |
| `in-addr.arpa` SOA、`a.ip6-servers.arpa` A 记录 | — | 212–257ms | — |
| 境外 IPv4 反向 | 约 200–380ms | 约 200ms（111.11.11.1 偶发 SERVFAIL） | — |
| 正向解析 | 1–4ms | 5–9ms | 20ms |

- 中国移动 DNS 对整个 `ip6.arpa` 都无法正常递归，只有自家 IPv6 段能回答；IPv4 反向和正向解析都正常。可能是运营商把 `ip6.arpa` 整体指向了只管自家地址段的内部服务器，这只是推断，无法验证。
- 光猫只是转发，表现和直接问运营商 DNS 完全一致。光猫的 IPv6 代理有一次 210ms 就返回了 APNIC 段的结果，换其他网段又全部超时，推测是运营商某台后端服务器正好有缓存。
- 公共 DNS 的冷查询耗时：119.29.29.29 约 55–62ms，223.5.5.5 约 0.4–1.7 秒。114.114.114.114 对所有反向查询都超时，不适合作为上游。

### 2.4 光猫侧检查（只读）

| 项目 | 现状 | 能否用来解决 |
| --- | --- | --- |
| 上网连接（PPPoE，IPv4 & IPv6）的 DNS | 自动获取上面 4 个地址 | 否：页面只在"静态 IP"方式下才允许手填 DNS；IPv6 的"DNS 获取方式"在页面源码里标注"暂缺"并被隐藏 |
| LAN 侧 IPv4"DNS 来源" | DHCP 固定下发光猫自己（192.168.1.1） | 否：这个选项只对上海、浙江的固件显示，本地固件把它隐藏了，接口也不返回这个字段 |
| LAN 侧 IPv6"DNS 来源" | 家庭网关代理 | 否：可以改，但路由器的 chinadns-ng 用的是 IPv4 的 192.168.1.1，改了也没有影响 |
| 按域名指定上游 | 不支持 | — |

- 把光猫改成桥接、由路由器自己拨号也解决不了，路由器拨号拿到的仍然是同样的中国移动 DNS。
- 就算能把下发的 DNS 换成公共 DNS，效果也和下面的方案二一样；而且运营商的远程管理（TR-069）可能会把设置改回去。
- 光猫管理界面同一时间只允许一个管理员登录，连续输错 3 次密码会锁定 1 分钟，用完记得点"退出"。

### 2.5 客户端为什么时好时坏

- `.217` 和 `.233` 都装了 Tailscale。systemd-resolved 会把反向查询同时发给 Tailscale 的 DNS（`100.100.100.100`），它有时会很快返回"查无此记录"；路由器上的 dnsmasq 也会缓存否定应答（`mini_ttl=3600`）。
- 所以客户端上的 ping 时快时慢。要判断是否修好，得在路由器这一层用新地址测。改动前用新地址测，两台主机经 systemd-resolved 的反向解析都卡满了 20 秒。
- 排查中走过的弯路：一开始从 `.233` 向 223.5.5.5、1.1.1.1 等发 UDP 53 查询，误以为"多个服务器都不回复，是权威 DNS 不响应"。实际上这些查询全被路由器劫持到了它自己的 dnsmasq，当时手工拼的 PTR 域名也写错了。测试上游 DNS 必须在路由器本机上做。

### 2.6 方案比较

| 方案 | 内容 | 效果 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| 一 | ArmWall 的 ping 加 `-n`，发 3 个包取平均，时限 5 秒 | 面板不再卡住，延迟接近真实往返时间 | 只解决 ArmWall 自身；面板显示的延迟会明显变小 | 待决定 |
| 二 | 把 chinadns-ng 的国内上游换成公共 DNS | 全网恢复 | 所有国内解析都换了上游，CDN 调度可能变差；公共 DNS 在这条线路上对 `*.gstatic.com` 出现过间歇性不回复 | 不采用 |

| 光猫 | 修改光猫的 DNS 设置 | — | 固件不支持；就算支持也等同方案二 | 不可行 |

## 3. 路由器改动：dnsmasq 的 ip6.arpa 上游（2026-11-10 08:34）

### 3.1 改动内容

```sh
cp -p /etc/config/dhcp /etc/config/dhcp.bak-20261110-0834
uci add_list dhcp.@dnsmasq[0].server='/ip6.arpa/119.29.29.29'
uci add_list dhcp.@dnsmasq[0].server='/ip6.arpa/223.5.5.5'
uci add_list dhcp.@dnsmasq[0].server='/d.f.ip6.arpa/'     # ULA fd00::/8，本地应答
uci add_list dhcp.@dnsmasq[0].server='/8.e.f.ip6.arpa/'   # fe80::/10，本地应答（下同）
uci add_list dhcp.@dnsmasq[0].server='/9.e.f.ip6.arpa/'
uci add_list dhcp.@dnsmasq[0].server='/a.e.f.ip6.arpa/'
uci add_list dhcp.@dnsmasq[0].server='/b.e.f.ip6.arpa/'
uci commit dhcp && /etc/init.d/dnsmasq restart
```

执行时 dnsmasq 重启了约 1 秒，代理和 chinadns-ng 都没有重启。生成的 `/var/etc/dnsmasq.conf.cfg01411c` 里有这 7 行 `server=`，passwall 原有的 `server=127.0.0.1#15354`、`no-resolv`、`all-servers` 都没变；重启后系统日志里没有报错。

### 3.2 为什么要加私有地址段的本地应答

在 dnsmasq 2.85 里，只要有一条按域名指定的上游能匹配查询名，`bogus-priv` 就不再生效（这个选项原本让私有地址的反向查询直接在本地返回"无记录"）。执行前用两个临时 dnsmasq 实例做了验证（只监听 `127.0.0.1:5398/5399`，不提供 DHCP，测完已删除）：

| 查询 | 现有 dnsmasq | 实例 A：只加 `ip6.arpa` | 实例 B：A + 私有段本地应答 |
| --- | --- | --- | --- |
| 境外 IPv6 反向（3 个网段） | 12 秒超时 | 71–228ms | 108–233ms |
| 局域网 ULA 的反向 | 1ms，本地应答 | 57ms，被发到了公共 DNS（返回里带着公共 DNS 才有的 `SOA localhost`） | 1ms，本地应答 |
| fe80:: 的反向 | 1ms，本地应答 | 54ms，被发到了公共 DNS | 1ms，本地应答 |
| IPv4 反向、正向解析 | 正常 | 不变 | 不变 |

### 3.3 与 passwall 的兼容性

- passwall 重启 dnsmasq 时（`helper_dnsmasq.sh` 里的 `logic_restart`），会先备份全部上游条目，只删除不带 `/` 的条目，重启后再把备份原样加回。实测它的备份命令能完整取到这 7 条。
- passwall 计算国内 DNS 时会跳过带 `/` 的条目（`app.sh` 里的 `DEFAULT_DNS`），结果为空，于是仍然回落到 `192.168.1.1`。
- `stretch()` 只在"所有条目都带 `/` 并且 `noresolv=1`"时才会动作。当前是 `noresolv='0'`，不受影响。
- 以上结论来自阅读脚本，并已实测：11:41 执行 `ifup wan6` 时 passwall 自动重启了两次（§6），之后 7 条规则都还在，生成的 dnsmasq 配置里也有，passwall 没有残留的备份项，chinadns-ng 的国内上游仍是 `192.168.1.1`。

### 3.4 验收

## 4. 其他发现

- **ping 回包是路由器代答的**：passwall 的 `accept_icmp='1'`、`accept_icmpv6='1'` 会生成 nat 规则，把发往非国内地址的 ICMP 重定向给路由器自己。例如 `-A PSW -p ipv6-icmp ... -m set ! --match-set passwall_chnroute6 dst -j REDIRECT`，IPv4 也一样。
  - 从 `.233`、`.217` ping 1.1.1.1、8.8.8.8、Cloudflare 的 IPv6、hknat，结果都是 0.5ms、TTL 64。dmit 拿到的是真实回包（约 208ms、TTL 47），原因尚未确认。
  - 所以对境外节点，面板的 ping 大多只能说明路由器在线。
  - 这两项在 11-03 的备份里就已经开着，不是那次改动带来的。
- **dmit 时好时坏是真实丢包**：发 3 个包丢了 1 个。面板显示 959ms，实际 ICMP 往返约 208ms，差出来的是启动进程和正、反向解析的耗时（见 §0 第 4 项）。
- **11-10 07:25 passwall 自动重启了一次**：光猫拒绝了路由器的 DHCP 续租（NAK），WAN 口重新拿到同一个地址后，passwall 按"WAN 上线即重启"的机制重启，局域网中断了几秒。
  - 当时排查还没有连到路由器，所以和排查操作无关。
  - 光猫当时已运行约 52 小时，推测是两天前重启过；光猫重启后拒绝旧租约的续租比较常见。

## 6. 问题五：局域网 IPv6 前缀失效（2026-11-10）

### 6.1 现象

手机 NekoBox（VPN 模式）连不上 dmit6 这个 IPv6 节点，之前一直正常。时间上紧接在 §3 的路由器改动之后，所以先怀疑是那次改动引起的。

### 6.2 证据

**手机日志（11-10 10:43，NekoBox debug 级别）**
- `dmit6.<域名>` 的 AAAA 能正常解析出来，说明 DNS 没问题。
- 但连接时报 `dial tcp [<节点IPv6>]:4431: connect: network is unreachable`，共 66 次；连国内的 IPv6 地址（`2409:8c1e:…`、`2409:8c20:…`）也报同样的错。
- 开头有 `network: missing default interface`。
- 这些是手机系统给出的错误，说明手机当时没有可用的公网 IPv6 地址或路由。日志里看不出连的是哪个网络，推测是家里 WiFi。

**路由器（11-10 11:15，只读）**

| 项目 | 现状 |
| --- | --- |
| 局域网前缀 `2409:8a04:5381:c8f1::/64` | `preferred: 0`（已作废），剩余有效期约 8 小时 |
| 光猫当前的 IPv6 委派前缀（光猫状态页） | `2409:8a04:5382:e1e0::/60`，和局域网在用的不是同一段 |
| 路由器 WAN 口 | 已经拿到了新段的地址（`…:5382:e1e0::2`） |
| odhcp6c 日志 | 连续 4129 条 `Server returned IA_PD status 'No Binding'`（11-09 09:06–09:50，更早的已被日志轮转覆盖），即光猫不认路由器要续租的旧前缀 |

**局域网主机**：`.233`、`.217` 的公网 IPv6 地址都是 `deprecated`，访问外网时只能选 ULA 地址（`fdca:…`）作为源地址，`curl -6 https://www.baidu.com` 两台都失败。

### 6.3 根因

- 光猫约在 11-08 重启过（11-10 07:47 查看时已运行约 52 小时），重启后从运营商拿到了一段新的 IPv6 前缀。
- 路由器的 odhcp6c 一直尝试续租旧前缀，光猫回复 `No Binding`。odhcp6c 没有因此丢掉旧前缀、重新申请，局域网就一直在用一个逐渐过期的前缀。
- 和 §3 的改动无关：§3 只改了 dnsmasq（DNS），给局域网分配 IPv6 地址的是 odhcpd，它从路由器开机后就没有重启过；`No Binding` 也早在 11-09 09:06 就开始了，比 §3 的改动早将近一天。

**为什么平时没人察觉**：局域网主机访问境外 IPv6 的 TCP 连接会被 passwall 的 TPROXY 交给 ArmWall 代理出去，ping 境外 IPv6 时又是路由器自己应答（§4），所以看上去一切正常。手机 NekoBox 在 VPN 模式下要直接用本机的 IPv6 连节点，不经过路由器的代理，所以第一个暴露出来。

### 6.4 处理（11-10 11:41）

```sh
ifup wan6
```

- wan6 重新申请了前缀，局域网拿到 `2409:8a04:5382:e1e1::/64`（光猫 `/60` 中的一段），`preferred` 约 48 小时，`valid` 约 72 小时。旧前缀暂时以 `deprecated` 状态保留，到期后自动消失。
- passwall 按"wan6 上线即重启"的机制自动重启了两次（11:41:46、11:41:58），每次局域网中断几秒。
- 没有修改任何配置文件。

### 6.5 验收

| 测试 | 处理前 | 处理后 |
| --- | --- | --- |
| 局域网前缀 | 旧前缀 `preferred: 0` | 新前缀 `…:5382:e1e1::/64`，`preferred` 约 48 小时 |
| `.233`、`.217` 的公网 IPv6 地址 | 只有作废的旧地址 | 各自拿到新前缀下的地址，并被选作访问外网的源地址 |
| `curl -6 https://www.baidu.com`（两台） | 失败 | 200，约 0.49 秒 |
| TCP 连接 dmit6 节点的 IPv6:4431（两台） | — | 成功（这类连接会经过 passwall 的 TPROXY，只能说明局域网到路由器这一段通） |
| IPv4 访问 | 正常 | 正常 |
| passwall 重启后：ipt2socks（IPv4 和 IPv6 的 1041 端口）、xray、chinadns-ng、dns2tcp、dnsmasq | — | 都在运行 |
| passwall 重启后：§3 的 7 条 dnsmasq 规则 | — | 都还在；境外 IPv6 反向解析 64ms |

手机端需要重新连接 WiFi（或开关一次飞行模式），拿到新前缀的地址后再验证。

### 6.6 后续风险

- 光猫每次重启都可能换前缀。路由器的 odhcp6c 遇到 `No Binding` 时没有自动重新申请，下次可能还会发生。
- 再次出现时：在路由器上看 `ifstatus wan6` 里的 `ipv6-prefix`，`preferred` 为 0 或者前缀和光猫状态页不一致，就执行 `ifup wan6`。
- 想要自动处理的话，可以加一个定时检查脚本，或者把 LAN 的 IPv6 改为中继模式直接用光猫的前缀。两者都还没有评估。
- **2026-11-25 补充更新**：2026-11-25 复现了光猫凌晨重拨换前缀导致 `check_ipv6.sh` v1 未检出、且 `.233` 卡死旧有状态 DHCPv6 `/128` 租约的故障。现已通过路由器关闭 LAN 有状态 DHCPv6（改纯 SLAAC + 无状态 DHCPv6）、升级 `/usr/bin/check_ipv6.sh` 至 v2（`/60` 前缀比对 + 国内白名单出站探活）及新增 `/etc/hotplug.d/iface/95-check-ipv6` 热插拔钩子彻底根治，详见 [INCIDENT-REPORT-2026-11-25.md](INCIDENT-REPORT-2026-11-25.md)。
